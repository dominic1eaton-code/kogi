1. What Hypergrid is

Hypergrid is the substrate — not an application. It provides the universal data layer that Kogi, Ume, and Qala are all built on top of. Its central claim: every domain entity is a row in an N-dimensional distributed spreadsheet, and building three different domain systems on the same substrate is better than building three separate storage stacks.

The conventional spreadsheet generalizes to N dimensions. Dimension 1 is the entity (rows). Dimension 2 is the field name (columns). Dimensions 3+ are domain-specific context axes — time periods, jurisdictions, audience segments, versions. Every cell at any coordinate carries a typed attribute map, not just a single value.

On top of this model, Hypergrid adds: per-attribute CRDT semantics for distributed consistency, an append-only EventLog for time-travel and audit, a typed property graph (Hypergraph) for entity relationships, an AI plugin interface for computed attributes, and a query language (HyperQL) that works across all dimensions.

2. The four layers

Every domain system built on Hypergrid follows this four-layer structure. The substrate layer is shared across all three systems. The bridge layer is the only place domain types touch Hypergrid primitives.

Presentation
Domain-specific APIs, UIs, CLIs, SDKs. Never exposes HyperCell or DimCoordinate to callers. Users interact in domain vocabulary — portfolios, org modules, solutions. Not rows and coordinates.
Domain logic
Business rules, lifecycle state machines, governance policies, domain workflows. Knows nothing about cells or dimensions. Operates on typed domain structs: Component, OrgModule, Solution.
Bridge (codec)
The DomainStore trait. The only place domain types map to Hypergrid primitives. Implements four methods: bootstrap() registers cubes and schemas, write() serializes entities to cells, read() deserializes cells to entities, exists() checks presence.
Substrate
Shared across all domain systems. Grid, Hypercube, UniversalCellStore, Hypergraph, EventLog, CrdtLog, VectorClock, HyperQL, AI plugin system, NamespaceRegistry, SpaceSystem, FederationManager.

3. The data model

Every entity in every domain system maps to the same universal layout. D₁ is the entity ID, D₂ is the field name, and the cell at that coordinate holds the typed value. Higher dimensions extend the schema for time-series, jurisdictional, segmented, or multi-tenant data without schema changes.

N Axis type Key type What it encodes
D₁ EntityAxis UUID The entity — portfolio item, org module, SDE, legal entity
D₂ PropertyAxis String The field name — "name", "status", "budget_spent", "health_score"
D₃ TimeAxis Timestamp Time period — quarter, sprint, fiscal year (KPI cubes, SDE snapshots)
D₃ CategoryAxis String Jurisdiction, audience segment, risk tier (Chombo, Soko, Qala CCRs)
D₄ CategoryAxis String Second classification axis — metric category, environment tier, cohort
Rule
Always start with N=2. Add D₃+ only when a cross-sectional query pattern is known and required — never speculatively. Never use a new axis for filtering that can be expressed as a D₂ attribute value filter. Never exceed N=6 for cubes with user-facing views.

Encoding strategies

How cells are stored depends on axis density. The hybrid strategy is right for almost all domain entity cubes.

D
Dense encoding
Full 2D array — every D₁×D₂ pair has a row. O(1) lookup. Use for small, fully-populated N=2 cubes. Fast but pre-allocates all combinations.
S
Sparse encoding
Key-value table — only non-null cells stored. O(log n) lookup via BTree index. Required for TimeAxis, GeoAxis, or any axis with >100K keys.
H
Hybrid encoding — recommended for all domain entity cubes
Dense base table for D₁×D₂ (entity × field, the hot path). Separate sparse extension table for D₃+ cells. O(1) for conventional 2D reads, O(log n) for higher-dimensional extension queries. Best of both worlds. Use this for kogi.portfolio.components, ume.kernel.modules, qala.solutions, and all primary entity cubes.

5. CRDT semantics

Every attribute key in every Hypercube must be assigned CRDT semantics at schema registration time. This is the most consequential design decision in the bridge layer — wrong semantics cause silent data loss in federated deployments. The rule: assign semantics based on what the field means, not how it's implemented.

Type Merge rule Use when… Examples
LastWriteWins Higher VectorClock timestamp wins. ActorId tiebreak. Single-valued field where the latest write is always correct name, description, status (v1), config, JSON blobs, boolean flags, reference IDs
OR-Set All concurrent adds survive. Removes are tagged — only remove the exact element they reference. Set-valued fields where concurrent additions from multiple users/nodes must both survive tags, owners, children, dependencies, members, toolbox_ids, approver_ids
GrowOnlyCounter Sum of all increments across all nodes. Decrement rejected with error. Monotonically increasing integers that can never decrease view_count, follower_count, restart_count, contribution_count
PNCounter Sum of (positive ops − negative ops) per node, merged across all nodes. Transactional accumulator that can go up and down budget_spent, hours_logged, allocated_units, stock_count
MaxRegister Maximum value always wins regardless of causal ordering. Version/sequence numbers that must never decrease version, schema_version, sequence_number, sprint_number
Lattice Merge to the least upper bound in the configured partial order. No backward transitions. Governed lifecycle states that must only advance (never regress without Admin override) ComponentStatus, SolutionLifecycleState, ModuleState, CCRStatus
AppendLog All appends from all nodes survive, causally ordered by VectorClock. Ordered audit trails and comment threads where every entry must be preserved activity_log, comment_thread, decision_history, audit_notes
LWW + System-only LWW with PermissionTier::Admin — no human actor can write. AI-computed signals that only AI engines should ever write health_score, risk_score, anomaly_flag, drift_status, compliance_prediction
Warn
The v1 lifecycle state gap: In v1, status fields use LWW — safe but not governance-enforced. Under a network partition, two nodes could disagree about whether a solution is Active or InReview. The v2 Lattice CRDT resolves this by encoding the valid state machine as a partial order, making invalid transitions a mathematical property of the data structure — not application code.

6. The write path

Every write to any entity in any domain system flows through this exact sequence. Understanding it is essential for building correct domain systems and for diagnosing latency issues.

01
Permission check
actor_tier ≥ attr.write_permission required. Logged as PermissionDenied event if rejected.
02
Policy engine evaluation
Allow / Deny / RequireApproval. Approval-pending writes are queued and return Pending status.
03
CRDT operation construction
VectorClock.tick(node_id) is called first. CrdtOperation::SetAttr (or AddToSet / IncrCounter / TransitionState) is constructed with the stamped clock.
04
Local merge (synchronous, in-memory)
Merge engine applies CRDT semantics for this attribute key. Losing LWW writes produce a ConflictRecord but don't fail.
05
Persistence (synchronous, PostgreSQL)
UPSERT on (grid_id, cube_id, dim_keys...). For batch writes: single transaction covering all fields — ~3× faster than individual writes.
06
EventLog append
Immutable entry: before_value, after_value, actor, vector_clock, timestamp. This is the audit trail and the AS_OF time-travel source.
07
CrdtLog append (federation delta)
Hot path: Redis LPUSH. Background flush to PostgreSQL. Used by peer nodes for delta sync.
08
Async fan-out (non-blocking)
AI invalidation (plugin queue), search index update, federation broadcast (Kafka), WebSocket push to collaborative editors. None of these block the response to the caller.
Opt
Batch write is the single most impactful optimization. grid.write_cell_batch(cube_id, ops, actor) executes all N field writes in one PostgreSQL transaction, one EventLog batch entry, and one Kafka message. For an entity with 30 fields, batch is ~3× faster than individual write_cell() calls. All bridge-layer write() implementations should use batch by default.

7. Technical concerns

Six meaningful technical concerns, graded by severity, with honest context for each.

!
Infrastructure overhead is high
The full production stack requires PostgreSQL, Redis Cluster, Kafka, ClickHouse (for large analytics), Meilisearch, S3, plus 5+ custom services (crdt-service, writeback-service, federation-coordinator, namespace-service, space-service). Most applications do not need all of this simultaneously.
!
Lifecycle state is LWW in v1
Status fields use LastWriteWins until v2 delivers the Lattice CRDT. Under a network partition, two nodes could hold different lifecycle states for the same entity, resolved by recency — not governance invariant. For Qala's pharmaceutical use case, this is a regulatory risk, not a theoretical one.
!
255-node VectorClock ceiling
The VectorClock is a HashMap<NodeId, u64> capped at 255 entries — one per federation peer. For large deployments, this means a hard limit on the number of active federation nodes per Grid. Each cell carries a VectorClock snapshot, so high-cardinality cubes compound the storage pressure.
!
Serialization overhead per field
Writing an entity with 30 fields produces 30 individual HyperCell writes if not batched. Each cell carries coord, attribute map, vector clock, actor ID, and audit trail metadata. The cell model is richer than a simple column update, and the overhead is real for hot-path entities.
!
Qala over-applies the spreadsheet metaphor
Kogi and Ume have data that genuinely wants to be a spreadsheet substrate. Qala's CI/CD pipelines, hermetic build environments, and SDE provisioning workflows are infrastructure automation problems — where GitOps tools (ArgoCD, Flux) already provide continuous reconciliation faster than Hypergrid's 15-minute drift detection SLA.
!
HyperQL expertise required
Cross-system queries, DimFold aggregations, and graph traversal require HyperQL fluency. The NL-to-HyperQL bridge helps end users but doesn't replace the need for platform engineers to deeply understand N-dimensional query planning. The learning curve is real and proportional to dimensionality.

8. Overhead remedies

Five concrete approaches to reducing Hypergrid's infrastructure costs, ordered from highest to lowest impact. Each accordion expands to a before/after and implementation guidance.

1
Tiered deployment: start SQLite, graduate to PostgreSQL
Highest impact

The CellStoreBackend trait is pluggable. The full PostgreSQL + Redis + Kafka + ClickHouse stack is one implementation. A SQLite-backed single-process implementation is a fully valid alternative that requires zero additional infrastructure. The Kogi desktop/mobile app and any single-user deployment should use SQLite exclusively and only introduce PostgreSQL when multi-node collaboration is actually needed.

Current (always)
  • PostgreSQL cluster
  • Redis Cluster
  • Kafka brokers
  • ClickHouse (analytics)
  • Meilisearch
  • 5+ custom services
Tiered (proposed)
  • Solo/mobile: SQLite only — zero extra infra
  • Team (2–10): PostgreSQL + Redis — no Kafka/ClickHouse
  • Production: Full stack, only when scale demands it

Implementation: formalize three GridProfile enum variants — Embedded (SQLite, no federation, in-process), Collaborative (PostgreSQL + Redis, Kafka optional), and Enterprise (full stack). Grid::new(config) selects the backend stack based on profile. Delta sync between Embedded nodes uses periodic file export rather than Kafka. This is already partially implied by the spec's storage_backend: memory | sqlite | postgres config field — it needs to be promoted to a first-class product decision.

2
Lazy services: defer Kafka, ClickHouse, Meilisearch until needed
High impact

Kafka is only needed for multi-node federation delta sync and AI writeback. If you have one node and no AI engines, you don't need Kafka. ClickHouse is only needed when analytics queries scan more than ~1M cells — irrelevant at small scale. Meilisearch is only needed for full-text search. These three components can be absent at startup and activated only when the feature that requires them is first exercised.

Current behavior
  • All infrastructure required at boot
  • Kafka connection verified in step 2 of Grid init
  • Meilisearch synced at startup
  • ClickHouse connection initialized regardless of query volume
Lazy activation (proposed)
  • Grid boots with PostgreSQL + Redis only
  • Kafka activated on first federation peer handshake
  • ClickHouse activated when scan_slice() receives >1M row estimate
  • Meilisearch activated on first searchable cube registration

Implementation: wrap each optional backend in a LazyBackend<T> that holds an Option<Arc<T>> and initializes on first use, logging a BackendActivated event to the EventLog. The FederationManager already has a concept of optional peers — extend this to the entire optional-service tier. This cuts the infrastructure requirement for a single-node Collaborative deployment from 6 services to 2 (PostgreSQL + Redis).

3
Narrow the AI infrastructure: WritebackService via HTTP, not gRPC+Kafka
Medium impact

The AI pipeline as specified requires: Kafka (for AI compute request routing), a WritebackService gRPC endpoint, separate AI engine processes (kogi-engine in Scala 3, ume-engine in Go+Python, qala AI Agent), and a Redis cache for AI signal results. This is a significant operational surface for what is conceptually just "compute a score and write it back to a cell".

Current AI pipeline
  • Cell mutation → Kafka topic
  • AI engine (separate process) consumes Kafka
  • Engine computes signal
  • WritebackService gRPC call
  • Cell updated with AiSignal value
Simplified pipeline
  • Cell mutation → in-process plugin queue
  • HypercubePlugin.compute() called in background thread
  • Result written via internal writeback
  • Kafka only for distributed deployments with remote engines

Implementation: the HypercubePlugin trait already exists and is in-process. For simple signals (health score, risk score, anomaly detection), the compute function is fast enough to run in a background thread pool within the Grid process — no Kafka, no gRPC, no separate service. Kafka + WritebackService gRPC should be reserved for heavyweight AI models (LLM inference, NL-to-HyperQL translation) that genuinely need to run in a separate process. The Scala 3 kogi-engine, specifically, is the right candidate for a separate service — but only once the Kogi platform has real users who need real AI signals.

4
Fix the VectorClock ceiling with Hybrid Logical Clocks
Medium impact

The current VectorClock = HashMap<NodeId, u64> stores one counter per federation peer. This has a 255-node hard limit (the spec's explicit ceiling), and each HyperCell carries a VectorClock snapshot — meaning high-cardinality cubes compound the storage cost. The correct fix is Hybrid Logical Clocks (HLC), which encode causality into a single (physical_time, logical_counter) pair without a per-node entry.

VectorClock (current)
  • O(N) bytes per cell per node
  • 255-node hard ceiling
  • Full clock stored on every cell mutation
  • Precise causality but high storage cost
HLC (proposed)
  • O(1) bytes per cell — always 16 bytes
  • No node count ceiling
  • Compatible with NTP-synchronized clocks
  • Preserves happens-before without per-node storage

Implementation: replace VectorClock with an HlcTimestamp { wall_clock_ms: u64, logical: u16, node_id: u32 } (16 bytes). The dominates() and happened_before() operations translate directly. The delta_since() operation becomes a time-range scan rather than a per-node comparison — which is actually simpler to implement and index in PostgreSQL. The 255-node ceiling is eliminated. This is a well-understood technique (used by CockroachDB, MongoDB, and others) with no loss of causal correctness.

5
Deliver the Lattice CRDT for lifecycle states in v1, not v2
Correctness

The current design defers the Lattice CRDT for lifecycle states to v2. This is framed as a simplification but it's actually a correctness gap — not a performance gap. Under a network partition, two nodes can drive the same entity to different lifecycle states, and the merge resolves to "whoever wrote last". For pharmaceutical drug approval or CCR governance, this is not acceptable at any scale.

LWW status (v1)
  • Node A: solution = "Approved"
  • Node B (partitioned): solution = "Draft"
  • Merge: whichever timestamp is higher wins
  • Governance invariant violated by network event
Lattice status (proposed)
  • Node A: solution = "Approved"
  • Node B: solution = "Draft"
  • Merge: join("Approved", "Draft") = "Approved"
  • State never regresses — enforced by data structure

Implementation: the Lattice merge engine is already fully designed and present in the v2 spec. The only implementation cost is: (a) a LatticeOrder struct defining the partial order for each lifecycle field, (b) a TransitionState variant in CrdtOperation (already specified), and (c) swapping SetAttr for TransitionState in the bridge layer's write() methods for status fields. The Lattice implementation is fully described — the gap is that it's been deferred rather than prioritized. For any domain system where lifecycle transitions have governance or regulatory meaning, the Lattice should ship in v1.

9. Deployment tiers

The proposed tiered deployment model maps each context to the minimum viable infrastructure. Moving up a tier adds capabilities but also operational cost.

Embedded
Solo · Mobile · Desktop · Offline-first
SQLite (cell store + EventLog)
In-process CRDT engine
In-process AI plugin queue
No external services
Delta sync via file export on reconnect

Examples: Kogi mobile app, Kogi desktop, solo developer Qala
Collaborative
Team · Small org · Up to ~50 nodes
PostgreSQL (cell store + EventLog)
Redis (cell cache + CrdtLog hot path)
Kafka optional — activate on first peer
ClickHouse optional — activate at 1M+ rows
Meilisearch optional — activate on search

Examples: Kogi cooperative, Ume team, Qala factory team
Enterprise
Large org · Federation · 50+ nodes
Full stack: PostgreSQL + Redis + Kafka + ClickHouse + Meilisearch + S3
Separate AI engine services (kogi-engine, ume-engine)
WritebackService gRPC
FederationCoordinator service
HybridLogicalClock (replace VectorClock)

Examples: Production Kogi platform, enterprise Ume, regulated-industry Qala
Key
The current design only specifies the Enterprise tier. Building Kogi first — at Embedded tier for mobile users and Collaborative tier for small cooperatives — removes the need to build and operate the full Enterprise stack before any users exist. The substrate upgrade path should be transparent: switching from SQLite to PostgreSQL requires no changes to the DomainStore codec or domain logic, only a config change in Grid::new().

10. Summary verdict

Hypergrid is a well-designed substrate with a genuine synthesis. The combination of per-attribute CRDT semantics within an N-dimensional model, an append-only EventLog that serves audit + time-travel + AI feature store simultaneously, a typed property graph with OR-Set edge semantics, and a unified AI plugin interface is more than the sum of its parts. These components individually are prior art — the integration is coherent and novel.

The current weakness is that the architecture documents only describe the full Enterprise deployment topology. There is no specified path from zero to production that doesn't require standing up eight services before the first user sees any value. The five remedies above — especially tiered deployment and lazy service activation — would reduce the operational barrier for Embedded and Collaborative deployments from "significant infrastructure project" to "single binary."

The correctness gap around Lattice CRDT for lifecycle states should be addressed in v1, not v2. Everything else is a performance or cost optimization. The fundamental architecture is sound.

+
What is genuinely innovative
Per-attribute CRDT semantics. OR-Set edge semantics on the Hypergraph. Consent Lattice on CrossGridLink. Cell-level provenance via ComputedFrom edges. Lattice CRDT for governance invariants enforced at the data layer.
+
What is prior art, well-executed
N-dimensional model (OLAP cubes). EventLog as source of truth (Datomic, event sourcing). AI feature store writeback (standard MLOps). HyperQL time-travel (bitemporal SQL). Plugin architecture (standard since Eclipse).
!
What needs immediate remediation
Lattice CRDT for lifecycle states — correctness gap, not v2 feature. Tiered deployment model — removes infrastructure barrier. Lazy service activation — cuts Collaborative tier cost significantly.
!
What is medium-term work
Hybrid Logical Clocks to remove 255-node ceiling. In-process AI pipeline for simple signals. Formal documentation of the three deployment tiers with migration path between them.
